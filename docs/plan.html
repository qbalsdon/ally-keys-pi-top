System Architecture

Signal flow

ally-keys.com connects to REC via Web Bluetooth. The Electron main process receives the keycode command string and fans it out to whichever HID workers have forwarding enabled. Each HID service runs in its own process bound to a dedicated Bluetooth adapter.

Wire Protocol

Command format (unchanged)

REC receives the exact same ASCII command strings the ESP32 receives over serial. No protocol changes are needed — only how ally-keys.com connects changes (Web Serial → Web Bluetooth write to NUS RX characteristic).

Example — Ctrl + Alt + Z

h0x00E0 / h0x00E2 / 0x001D / r

Token reference

  • hXXXX — hold modifier (Control, Alt, Shift…)
  • XXXX — press key (4 or 6 hex chars per device capability)
  • / alone — release all (clear buffer)
  • r — terminate, send HID report
  • v — version probe; REC replies with version string on TX

REC — Nordic UART Service (NUS)

GATT UUIDs

  • Service: 6e400001-b5a3-f393-e0a9-e50e24dcca9e
  • RX (write from ally-keys.com): 6e400002-b5a3-f393-e0a9-e50e24dcca9e
  • TX (notify to ally-keys.com): 6e400003-b5a3-f393-e0a9-e50e24dcca9e
  • Advertised name: ally-keys-REC

2
BLE HID services (HID 1–4)
BLE · HOGP

Implement HID over GATT Profile for keyboard emulation. Each of the 4 services is an isolated child process bound to its own adapter.

HOGP GATT profile per worker

  • HID Service 0x1812
  • Report Map 0x2A4B — standard USB keyboard descriptor
  • Input Report 0x2A4D — 8 bytes (modifier + 6 keycodes)
  • HID Information 0x2A4A — [0x01,0x11,0x00,0x03]
  • HID Control Point 0x2A4C — write-only
  • Battery Service 0x180F — static 100%
  • Advertised names: AK-HID-1 through AK-HID-4

Process model

  • Main spawns 4 workers via child_process.fork('ble/hid-worker.js')
  • Each worker env: BLENO_HCI_DEVICE_ID=1 … =4
  • IPC message from main → worker: { type:'report', data:Buffer<8> }
  • Worker re-advertises automatically on disconnect
  • Main tracks each worker's connected state and notifies renderer
3
BLE REC receiver service
BLE · NUS

NUS GATT service on hci0. Parses ally-keys wire protocol, converts to HID reports, dispatches to forwarding-enabled HID workers.

Tasks

  • Implement NUS with bleno on BLENO_HCI_DEVICE_ID=0
  • Port keymap.js → ble/protocol-parser.js (same keyMap + toKeyCode(), Node.js module)
  • Parser output → 8-byte HID report builder
  • Dispatch report to each worker whose forwarding flag is true
  • TX notify: version string on v probe; "1" if no HID connected
ℹ
protocol-parser.js is a direct port of the existing keymap.js — same map, same logic, zero protocol changes. ally-keys.com sends identical strings whether talking to the ESP32 or to REC.

6
Pi system configuration
System · BlueZ

Configure BlueZ for multiple adapters, auto-accept pairing, discoverable timeouts, and the Electron autostart chain.

BlueZ

  • Confirm all adapters: hciconfig -a
  • /etc/bluetooth/main.conf: DiscoverableTimeout=0, FastConnectable=true, Privacy=off
  • Auto-accept pairing: register NoInputNoOutput agent via dbus-next in main process
  • Mark each adapter discoverable: bluetoothctl select hciN && discoverable on
  • Grant Node CAP_NET_ADMIN + CAP_NET_RAW via setcap on the Electron binary (avoids running as root)

Autostart

  • start.sh: brings up all adapters (hciconfig hciN up), sets DISPLAY=:0, launches Electron
  • Entry in ~/.config/lxsession/LXDE-pi/autostart: @/home/pi-desk/ally-keys-pi/start.sh

Design Decisions

Key choices

Why NUS for REC?
NUS is the de-facto BLE UART bridge. Web Bluetooth supports it without flags, and the ally-keys wire protocol is ASCII text — it maps directly to a byte-stream characteristic. No protocol redesign needed.
Why fork per HID?
bleno targets one HCI adapter per process via env var. 4 forks × 1 adapter = 4 independent HID devices, each with its own bonding state and advertising lifecycle.
Why reuse the renderer?
The peripheral page is a complete, tested keyboard UI. Porting to Electron requires replacing only the transport layer. Months of UI work reused by changing two files.
REC not toggleable?
REC is the inbound receiver — disabling it would cut all input. Only HID 1–4 are toggled; a disconnected HID chip is shown but its tap is a no-op.
Auto-accept pairing?
A NoInputNoOutput BlueZ agent via dbus-next handles HID bond requests silently. Bonding is persisted by BlueZ — phones reconnect automatically on boot.
Web Bluetooth browser support?
Chrome/Edge desktop + Chrome Android. iOS/Safari excluded (no Web Bluetooth). The Web Serial path stays for non-BLE use; both coexist in the ally-keys.com navbar.
